# Архітектура модульної CRM

## Роль PostgreSQL

PostgreSQL є центральною базою обміну між модулями. Він не замінює 1C як основну облікову систему, а працює як інтеграційний центр для оперативних CRM-даних.

## Межі відповідальності

`1C`

- головна система для номенклатури, цін, залишків, бухгалтерських документів;
- передає довідники в PostgreSQL;
- отримує підтверджені замовлення з PostgreSQL.

`core`

- єдині клієнти, товари, склади, залишки, ціни, замовлення;
- нормалізовані дані, з якими працюють усі модулі.

`integration`

- `inbox_events` приймає події від зовнішніх модулів;
- `outbox_events` містить події, які треба відправити в модулі;
- статуси подій дозволяють повторювати обробку після помилок.

`marketplace`, `website`, `b2b`, `retail`

- окремі схеми для специфічних таблиць модулів;
- спільні сутності зберігаються в `core`, щоб не дублювати клієнтів, товари й замовлення.

## Потоки даних

1. 1C передає товари, ціни та залишки в PostgreSQL.
2. Сайт, marketplace, B2B і retail читають актуальні товари, ціни й залишки.
3. Канали продажу створюють замовлення або події в `integration.inbox_events`.
4. Сервіс синхронізації перевіряє подію, створює записи в `core.orders` і `core.order_items`.
5. Підтверджені замовлення потрапляють в `integration.outbox_events` для передачі в 1C.
6. 1C повертає статуси документів, оплат, відвантажень і закриття замовлень.

## Чому outbox/inbox

Прямий запис із кожного модуля в усі таблиці швидко створює хаос. Модель inbox/outbox дає:

- журнал усіх обмінів;
- повторну обробку після помилки;
- контроль статусів;
- можливість підключати нові модулі без зміни всієї системи.

## Наступні міграції

Після першого запуску варто додати:

- ролі та права доступу для кожного модуля;
- таблиці мапінгу зовнішніх ідентифікаторів;
- API-ключі або service accounts;
- детальні таблиці доставок, оплат, повернень;
- регламент обміну з 1C;
- моніторинг помилок синхронізації.
